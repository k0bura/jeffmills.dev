## Overview

I work with two teams at Vanguard FAS: the team behind the Meridian design system and the team behind Expert Insights. I write code alongside the design system engineers, and on both teams the mentoring shows up as much in PR reviews and pairing sessions as in 1:1s. Mentoring and contribution overlap and never stop for me. This is how I think about both.

I&rsquo;d rather build the system that teaches the pattern than have the same conversation twice.

## How I mentor

### How I calibrate

How I work with each engineer depends on where they are in their career arc. The voice I use changes, and the structure of the feedback stays the same.

**With newer engineers**, I open with genuine, specific recognition: *&ldquo;you&rsquo;re technically strong, you show up in discussions&rdquo;*. Then I state a behavioral gap, which describes what they do and doesn&rsquo;t assess their character. I close by saying I believe in them: *&ldquo;the talent is there; I need the discipline to match it.&rdquo;* I don&rsquo;t soften it. I say the hard thing directly, once, clearly.

**With mid-level engineers**, the most useful thing I can do is invite them into the actual problem-solving instead of receiving the problem from them. The ask I make is explicit: *&ldquo;help me think through how we staff this, how we prioritize, where we can create the most impact, don&rsquo;t just flag the problem.&rdquo;* I pair the invitation with scaffolding: named collaboration, protected time, and direct coaching on confidence where needed.

**With senior engineers and tech leads**, the conversation turns outward. The patterns and architectural guidance they&rsquo;ve developed have broader value than the team they are on. The growth move is to make those patterns visible: reusable frameworks, demos, architectural notes for other teams. *&ldquo;You don&rsquo;t need to wait for a formal venue. Start creating them.&rdquo;*

**With my peers**, I give an honest diagnosis as an equal. I name systemic patterns (breadth diluting impact, speed without architectural grounding, narrative updates where decisions should be forced) and the structural fix, and I don&rsquo;t soften either.

### The shape of the feedback

Every piece of substantive feedback I write follows the same structure:

1. I give genuine, specific recognition of what is working.
2. I state the growth edge as a behavioral or strategic gap, with no judgment attached.
3. I give a concrete path forward and say I believe it&rsquo;s achievable.

I always pair acknowledgment with challenge, and I do it deliberately: *&ldquo;I set a high bar intentionally because I believe in the team.&rdquo;*

### Teaching through infrastructure

This is the most distinctive part of how I work. **I don&rsquo;t rely on repeated conversations to enforce standards. I build the infrastructure that makes the correct pattern the default path.**

On Meridian, migrating a V0 component to V1 means reading the architecture docs, consulting accessibility patterns, applying composable APIs correctly, and following a slot-over-props philosophy. It&rsquo;s a multi-step discipline that&rsquo;s easy to skip under deadline pressure. So I encoded the entire workflow as a structured Claude Code skill (`/build-v1`) that mandates reading the architecture docs *before* any code is written. The accessibility patterns are required reading too, through the repo&rsquo;s agent instructions. The standard is no longer carried in a person&rsquo;s head or enforced in code review after the fact. It runs before the first line of code.

The same idea applies to documentation quality. Instead of &ldquo;we should write better docs,&rdquo; the team has a `/test-docs` skill that simulates a fresh agent session, follows the exact discovery path, and produces a Pass/Partial/Fail checklist with a percentage. Doc quality stopped being a gut feel and started being a tracked metric.

For me, mentoring at scale means building the system that teaches the pattern so we all use it.

## How I contribute code

### Reuse first

I evaluate technical work through the lens of compounding value. A contribution that works once is table stakes. When I see a contribution that works for the next three teams, I name it out loud:

> Your data-visualization content-fragment architecture sharply reduced hard-coded content and created a reusable data pipeline that&rsquo;s the foundation for all future content-fragment implementations. That&rsquo;s the kind of forward-thinking architecture I want more of.

When I review my own work, the standard is the same: *I push for designs that support progressive phases without requiring a rewrite at each stage.* Future-proofing is how I judge whether a design will still be useful three years from now.

### Clean baselines first

I don&rsquo;t ship new capabilities on top of technical debt when I can avoid it. On Meridian, the legacy-to-current conversion backlog was executed as a prerequisite to the V3 architectural work. It was the right call to prevent adoption fragmentation and long-term friction for consumers.

The pattern is to establish a clean baseline, then build forward. Debt cleanup is what makes the next thing survivable.

### AI-native design

My clearest technical conviction is that AI integration is a first-class architectural concern, and I don&rsquo;t treat it as a layer applied after the fact. The benchmark I hold myself to: *&ldquo;&lsquo;understand and apply AI tools&rsquo; sets a low bar. The intent should be workflow-level change, not tool familiarity.&rdquo;*

This shows up in the actual contribution work. The Meridian design system:

- Generates machine-readable component metadata (`meridian.web-types.json`, `meridian.html-data.json`) at every build, so every developer&rsquo;s editor understands the component API automatically.
- Ships an MCP server (`meridian-mcp`) exposing 9 tools across components, design tokens, and recipes, making the entire design system queryable by any AI assistant without fine-tuning or RAG.
- Uses Claude Code skills to enforce architecture patterns through agentic workflows instead of relying on code review.

The framing I use for the IDE metadata layer: *&ldquo;Before any AI agent enters the picture, the authoritative component API needs to be machine-readable and editor-discoverable. That&rsquo;s the foundation every other layer depends on.&rdquo;*

The closed loop: the design system generates its own AI-readable documentation at build time, which feeds both external AI assistants and internal agentic workflows, and documentation quality is measured by an automated AI audit. The system continuously improves its own AI-readiness. See [Design System + AI: The Three-Layer Architecture](/case-studies/07-design-system-ai-architecture) for the full technical breakdown.

### Documentation as an engineering deliverable

I treat documentation quality as a first-class engineering metric. The `/test-docs` audit skill exists because we needed a way to answer a specific question: are our docs actually sufficient to guide an AI agent through building a component correctly?

The answer is now measurable, trackable, and improvable, with a percentage score and a structured checklist. It used to be a gut feel. The underlying principle extends beyond AI tooling: documentation that can guide a capable agent can guide any new engineer. The bar is the same.

## What both have in common

How I mentor and how I contribute come from the same instincts applied at different scales.

In both cases, I encode the standard in the system instead of carrying it in my head. I make the right path the default path. I measure quality explicitly so improvement is visible. I calibrate the work to where someone (or something) actually is.

What I want from the work:

- I want the patterns I&rsquo;ve worked out to be usable across the org as well as inside my team: migration kits, templates, education sessions, the things that travel.
- I want an experimentation-driven culture that uses GenAI tools as workflow change, beyond chat assistants.
- I want a team that doesn&rsquo;t need me in the room for the architecture to stay coherent.

The Meridian MCP server, the V1 migration skills, and the documentation quality audit are each a working prototype of that. This case study is the pattern, already running.
